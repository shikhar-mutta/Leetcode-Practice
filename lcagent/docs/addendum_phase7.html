A.3 A correction to Q18

Q18 answers the charge that the fetcher needs the network by saying it “tries the on-disk cache first, then the local archive of ~3,350 solutions, and only then the network”. That described the degradation I had designed. The code did not do it: it called LeetCode first and reached the archive only when that call failed, which is the opposite order and means the good data was reached by accident rather than by design.

The code now does what the answer says. If this comes up, the version worth giving is the unflattering one: I described the behaviour I intended, found the implementation inverted when I went to change something else, and fixed it. The answer's conclusion — that an archived problem works with no connection — is true now, and is stronger than it was: the question file travels with the scaffold, so there is no network call left in the path at all.

A.4 Questions

Q51  Your fetcher went to the network first and treated your own archive as a fallback. Why was that the wrong way round?

Three costs, in order of weight. The archive holds the repaired drivers. Those 3,356 folders are not a cache of what LeetCode would give me — they are what I had to fix: hand-written readers for odd input notations, self-validating harnesses for special judges, corrected expected files. Fetching fresh regenerates the broken version of exactly the problems that cost the most work.

It put a network call in the common case. The common case is re-solving a problem I have already done, which is what the archive is for.

A fallback that only runs on failure is untested. It ran when LeetCode was down, which is rarely, so its behaviour was the least exercised path in the system.

What I gave up: the archive can hold a stale scaffold — 430's input file is literally the word placeholder — so --live skips the archive and fetches fresh, and a problem whose archive entry is missing or empty falls through to LeetCode automatically, saying which files were missing.

Q52  You hand back an empty stub instead of the stored solution. How do you know the stub is correct?

Because correctness here has a mechanical definition: the stub must compile against the same driver the archive ships beside it. So I compiled all of them. Every stub the archive can produce — 3,355 of them — compiles against the driver archived beside it.

The first run passed 3,351 of 3,356, and the five failures were the useful part. Two signatures used ll, an alias declared inside the class body I was deleting. One carried a user-added default argument (int ans = INF3455) that is not part of LeetCode's API. One kept an out-of-class vector<int> Solution::v; definition for a member that no longer existed. One had a template default argument (uint8_t RBITS = SBITS) that my segmenter read as an initialiser, so it swallowed the class that followed. The fifth was not a bug: 3795's archive entry is four empty files, and there the fetcher correctly falls through to LeetCode.

What the test does not prove is that the stub is the signature LeetCode would give — only that it is the signature the driver calls. Those agree for every problem the archive has, because the driver was generated from LeetCode's own snippet.

Q53  Why re-derive the stub every time instead of storing one per problem?

A stored stub is 3,356 more files that can drift from the driver sitting next to them. The derivation reads the driver to decide which methods are the API — whatever it calls survives, private helpers and members do not — so the stub cannot disagree with the harness that calls it.

It also buys a property I use elsewhere. The rebuild is idempotent, so make_stub(x) == x is exactly the test for “this file is still the untouched stub”. That is how clearing the root knows not to rescue an empty file into data/replaced/, where it would overwrite a genuine rescued solution with the same id. No marker file, no extra state, no way for the two to disagree.

Q54  Why is the judge's mock in the driver and never in the file you submit?

284 taught me this one, by failing on the judge rather than locally. Its Iterator base class is supplied by LeetCode at submission time. A concrete class Iterator {...} inside 284.cpp compiles perfectly well on my machine and is a redefinition error the moment the file is submitted.

So the mock goes in the driver, above its #include "<id>.cpp": only the local harness ever sees it, and the file I submit declares nothing the judge already provides. NestedInteger is handled the same way. Hidden APIs are the mirror image — the stub carries the declaration int guess(int num);, which a judge accepts as a redeclaration, and the driver carries the definition backed by that case's extra input line.

The cost is IDE diagnostics on the solution file alone, which cannot see the base class. That is noise I accept; the alternative is noise the judge rejects.

Q55  LeetCode calls six different structures Node. How do you tell them apart, and why does it matter?

By their fields, most specific first: neighbors is a graph vertex, children an n-ary tree, random a list with random pointers, child a multilevel list, topLeft a quad tree, and a bare next beside left/right a tree with next pointers.

It matters because the name carries no information and each one arrives in a different notation: an adjacency list, a level order with nulls closing each child group, [[val, random_index]], levels separated by null runs, [isLeaf, val] pairs. Reading one as another does not crash — it silently builds the wrong structure. Every variant exposes the same three names (_toNode, _sNode, _rnode), so the type tables need one entry for Node* and the variant is chosen once, from the definition.

The quad tree needed one extra piece of honesty. LeetCode states that a non-leaf node's val is not compared, and its own examples disagree with each other — 427 prints a 1 there, 558 prints a 0. The printer emits [0, *] for a non-leaf and the expected file is normalised the same way, so the test checks the structure and not a value the judge ignores.

Q56  You changed a generator that 3,356 problems depend on. How did you know you had not broken it?

Differential testing against the previous version, not judgement. I kept the old generator, ran both over every problem with cached metadata — 3,083 of them — and compared the files they wrote. For 3,036 the output is byte-identical apart from helper functions the new one adds, so the behaviour cannot have changed and no compilation is needed. That shortcut is what makes the test affordable.

For the 47 that differ I compiled and ran both: each generated driver was fed the archived solved solution and its output diffed against LeetCode's own expected values. 40 pass that did not before — the six Node variants, NestedInteger, guess, isBadVersion, the Codec round trips, PeekingIterator — and nothing regressed.

The test also found a gap I had not gone looking for: 19 problems return vector<bool>, which the generator had never been able to print.

Q57  What still does not work?

Seven problems fail on the LeetCode path, and all seven failed before. Three (384, 519, 470) return random values, so no fixed expected file can match them; they need a self-validating driver, which is a per-problem judgement and not something a generator should guess. Three (843, 1095, 1237) use judge classes I do not mock — Master, MountainArray, CustomFunction — and there the fetcher prints a warning naming the class and where the mock belongs. One (1462) is an output mismatch I have not diagnosed.

Concurrency problems get a driver that refuses to pretend: it compiles, prints that a thread harness is needed, and exits non-zero. A generated harness would have to know what the input means for each problem — thread start order for 1114, a count for 1115, a water string for 1117.

All ten are in the archive with working drivers, so option 1 — the path actually used — handles every one of them.

Q58  You wrote something that reads C++ to do this. Is that not the wrong tool for the job?

It is not a parser and I would not defend it as one. It blanks comments, string and character literals and preprocessor lines, then scans braces and parentheses — enough for the shapes LeetCode solutions take, and nothing beyond them.

Two things make that acceptable. The failure mode: when it cannot find a solution class it returns nothing, and the fetcher falls through to LeetCode rather than writing a file that is subtly wrong — the same rule as the rest of the fetcher, which modifies nothing when it fails. And the test set: 3,356 real solutions, every one compiled, including the deliberately pathological ones — a copied solution carrying AVX intrinsics and attribute macros, classes using tabs, a solution whose helper is defined outside the class.

The alternative is libclang: correct by construction, and a dependency that has to exist on Windows too, which is a requirement this project actually has. The measured benefit would have been five files out of 3,356, all five fixable in an afternoon. I would revisit that decision the first time a sixth class of failure appears rather than defending the scan on principle.
